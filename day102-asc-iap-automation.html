The one ASC web step that breaks every IAP submission automation

Apple's rejection emails name the category, never the field. Here's the hidden step that costs indie devs weeks — and why the REST API can't do it for you.

The trap: "In-App Purchase completeness issue."

You check your IAP code. The code is fine. Product IDs match. So what's actually wrong?

Your IAP was never attached to this review submission. Apple literally never saw it.

The hidden "Add for review" step

App Store Connect has a separate toggle on the app version page. Miss it, and Apple's automated check flags 2.1(b) — before a human ever opens your build.

Before every submission: 1. GET /v1/apps/{id}/inAppPurchasesV2 -> every IAP state must read WAITING_FOR_REVIEW or APPROVED -> NEVER READY_TO_SUBMIT (30-min auto-reject loop) 2. On ASC version page: toggle each IAP "Add for review" -> The REST API cannot do this step. -> POST /v1/reviewSubmissionItems accepts exactly: appStoreVersion / appCustomProductPageVersion / appEvent -> Every IAP relationship type -> 409 error.

Why the API can't help

If you automate submissions through the API (many indie devs do), the "Add for review" step is the one thing you still have to do by hand in the web UI. That's the gap that burns weeks — not your code, not your IAP configuration, just the missing checkbox.

7 of 8 apps live on the App Store. The 8th is in its first review. Every one taught me a different way Apple's rejection emails hide the actual field.

Pre-flight that would have saved me weeks

Before every submission:

  • GET /v1/apps/{id}/inAppPurchasesV2 — check every IAP state
  • On ASC version page: confirm each IAP is toggled into the review submission
  • Confirm the IAP review screenshot is uploaded
  • Then submit
